# protodatabase

**Protobuf messages are the single source of truth for the database.** You write
one `.proto`, and the SQL schema, migrations, and a typed (Kysely-style) client
all fall out of it — no hand-written SQL, no per-field mapping layers, no
separate backend/frontend types.

## CLI

```
bun protodatabase/cli.ts <database.proto> \
  --gen-dir    <dir>   \  # protoc-gen-es *_pb.ts messages
  --schema-out <file>  \  # raw CREATE TABLE / CREATE VIEW DDL
  --types-out  <file>  \  # the `Schema` type (table → row types)
  --client-out <file>  \  # module exporting open…(sqlite) → typed client
  [--message Database] [--open-name openFooDb] [--proto-path <dir>]...
```

You choose every output path. The app database in this repo is generated by
`bun run gen:db` (see package.json) from `src/proto/models/database.proto`.

The framework self-test lives under `protodatabase/`: `bun protodatabase/demo.ts`.

## The idea

`message Database` *is* the schema. No custom annotations — a table is just a
message field, so the file stays plain proto and every existing proto tool keeps
working.

- **Every field of `Database` is `repeated <Message>`** — one rule, no
  exceptions. A relational database is a set of rows, so a table is always
  `repeated Row`. No `map` (a keyed table is just a row carrying its own `key`
  field), no singletons (a one-row table is just a table with one row). The
  generator rejects any non-repeated field.
- **Each field of a row message is a column.**
  - scalar (`string`/`double`/`bool`/`int…`) → a typed SQL column you can filter on
  - anything else (nested message, `repeated`, `map`) → a **BLOB** holding that
    field's raw protobuf encoding. No child tables; nested data rides along as
    bytes and stays schema-evolvable for free.
- **Primary key** = the row's `id` (or `key`) field, if present; otherwise the
  table is keyed by SQLite's implicit rowid and inserts append.

Physical columns are named by **field number** (`f1`, `f2`, …) and tables by
number (`t1`, `t2`, …) so renames in the `.proto` never touch stored data. A
generated **VIEW** per table restores the real field names, so the database is
still readable at a plain `sqlite3` prompt.

## Files

| file | role |
|------|------|
| `proto/db/v1/database.proto` | the schema — `message Database` of tables |
| `gen/**_pb.ts` | protobuf-es reflection (regenerate with `bun run gen`) |
| `plan.ts` | descriptor → tables + columns + `CREATE TABLE`/`CREATE VIEW` DDL |
| `codegen.ts` | writes `schema.sql` + `db.gen.ts` |
| `schema.sql` | generated raw DDL |
| `db.gen.ts` | generated `Schema` — table → `{ select, insert }` row types |
| `client.ts` | the Kysely-style typed `Db` |
| `demo.ts` | runnable walkthrough of every table shape |

## Client

A Kysely-style, fully typed query builder. Table names, column names and every
value are checked against `db.gen.ts` — whose row types come straight from the
protobuf messages, so nested fields keep their real proto types.

```ts
const db = createDb(new Database("data.sqlite3"));
db.migrate();                                         // additive reconcile, idempotent

db.insertInto("meals").values({ id: "m1", name: "lunch" }).execute();
db.insertInto("nutrition").values({ key: "chicken", protein: 31 }).execute(); // map: row carries `key`
db.insertInto("profile").values({ proteinDiv: 5 }).execute();                 // singleton

db.selectFrom("meals").selectAll().where("name", "=", "lunch").execute();     // → SELECT * FROM t1 WHERE f2 = ?
db.selectFrom("meals").select(["id", "name"]).execute();
db.selectFrom("profile").selectAll().executeTakeFirst();

db.updateTable("nutrition").set({ gi: 70 }).where("key", "=", "rice").execute();
db.deleteFrom("meals").where("id", "=", "m2").execute();
```

You write proto field names; the builder translates them to `fN` columns. Reads
decode BLOB columns back into real nested proto messages. Equality-style filters
(`= != < <= > >=`) only — for anything richer, query the generated views in real
SQL. Filtering on a BLOB (nested) field is rejected, since those columns are
opaque bytes.

## Migrations

`migrate()` diffs the descriptor against the live schema (`PRAGMA table_info`)
and applies additive changes only: a new table → `CREATE TABLE`, a new field →
`ALTER TABLE … ADD COLUMN`. It's idempotent, so there is **no migration ledger** —
"done" is derived from the database itself. Because columns are keyed by field
number, an old row simply gets `NULL` in any column added later.

## Known non-goals (prototype)

- No relations/joins, no query builder — by design.
- Primary keys are convention (`id` field, or the map key), not declared.
- Cross-row data moves (recompute an aggregate, promote a BLOB field to its own
  column) aren't covered by additive migration; those stay as one-off backfill
  scripts.
